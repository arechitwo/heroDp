# 영웅 설계 초안

구이 몬태그 영주와 플레이어별 4슬롯 기반 구조를 구현한다. 아래 12종 인물·능력·수치는 확정 데이터가 아닌 논의 초안이며 아직 구현하지 않았다.

## 영주·영웅 기반 구조 작업 분리

기반 구조 구현은 PR #5의 브랜치 feature/unit-roster-cleanup을 베이스로 하는 PR #6에서 진행한다. PR #5의 리뷰·머지 후 PR #6의 베이스를 main으로 변경하여 영웅 관련 변경만 리뷰한다.

- 플레이어마다 영주를 포함한 영웅 4슬롯을 둔다. 첫 슬롯은 구이 몬태그 영주, 나머지 3슬롯은 추가 영웅이다. 영주 7명과 추가 영웅 21명으로 전체 실체 슬롯은 28개다.
- 영웅 생성 시 CUnit과 해당 영웅의 스킬 처리 함수를 슬롯에 연결한다. EUDFunc 계열의 함수 포인터 저장·호출 API를 확인한 뒤 적용한다.
- UnitGroup은 런타임 함수 인자로 전달하지 않는다. 부대 그룹은 빌드 때 선언·연결한다.
- 그룹을 여러 번 순회하지 않도록 기존 순회 안에서 실행할 유닛별 처리 콜백을 함수 포인터로 전달하는 구조를 검토한다. 명령 여부와 무관하게 매 틱 dying 항목을 정리한다.
- 스킬의 지점형·유닛 대상형·자기 강화형을 공통 명령으로 받아, 영웅별 함수에서 목표 좌표·ptr·자기 자신으로 해석한다.
- 빌드와 테스트는 별도 요청이 있을 때만 실행한다.

### 구현된 연결 구조

- hero_state.HEROES는 EPD를 저장하는 일반 EUDVArray(28)이다. P1은 0~3, P2는 4~7, … P7은 24~27이고 0·4·8·12·16·20·24는 영주다. heroes.tick은 런타임 for로 순회하고 EPD 0은 즉시 건너뛴 뒤 CUnit.cast한다. CUnit 타입 배열은 상수 0 대입을 허용하지 않으므로 사용하지 않는다. 스킬 대상 EPD도 지점형의 0을 허용하는 일반 배열이다. 죽었거나 재사용된 CUnit이면 세대값을 확인해 슬롯과 콜백을 비운다.
- SKILLS와 MEMBERS는 함수 포인터 값을 저장하는 EUDVArray다. SKILLS를 읽으면 SkillFunc.cast로 EUDFuncPtr(4, 0)로 감싸 (슬롯, 영웅 EPD, 목표 좌표, 목표 EPD)를 전달한다. MEMBERS는 MemberFunc.cast로 EUDFuncPtr(2, 0)로 감싸 (슬롯, 부대원 EPD)를 전달한다. 함수 포인터는 2필드 구조체이므로 배열에는 해당 구조체 참조를 저장한다. 모든 캐릭터 함수를 호출한 뒤 내부에서 종류를 검사하지 않고, 생성 시 선택해 저장한 함수만 호출한다.
- 생성 직후 state.bind(slot, unit, skill, member)로 CUnit·세대·스킬 함수·부대원 함수를 함께 연결한다. 시작 시 기존 수도 주변에 영주 1명을 생성하며 별도 신규 유닛 추적으로 다시 등록하지 않는다.
- 영주는 Gui Montag ID, HP 8000·실드 1·방어력 30·영웅 방어·기본 일반 화염 공격력 200·공격 간격 30의 초기값이다. 기존 화염 범위 공격을 유지하며 9번 액티브 능력은 아직 정하지 않았다. 현재 영주 스킬 콜백은 추가 효과가 없는 패시브 처리다.
- LORD_ARMIES는 각 플레이어 영주 슬롯의 부대이며 나머지 3개 그룹도 플레이어별로 미리 선언한다. 현재 신규 일반 병력은 groups.add_lord(epd)에서 모두 현재 소유자의 영주 부대로 등록한다. 군영에서 태어나는 유닛도 다음 신규 유닛 처리에서 같은 경로를 사용한다. 영주 본인은 부대원에 포함하지 않는다. groups.add_hero_member(slot, epd)는 새 부대원을 지정 슬롯에 등록하는 기반 API다. 이미 다른 그룹에 들어간 유닛의 이동 API는 아니며 중복 등록하면 안 된다.
- state.request_skill(slot, target_pos, target_epd)로 동기화된 스킬 요청을 넣으면 heroes.tick이 등록된 함수 포인터를 호출한다. 개별 스킬의 대상 조건·마나·쿨다운은 해당 핸들러에서 구현한다.
- state.request_command(slot, command, target_pos)의 command는 1=부대 공격, 2=부대 이동이다. 기존 commander의 단일 그룹 순회 안에서만 부대원 콜백을 실행하고 dying 항목을 매 틱 정리한다. 전군 명령과 겹치면 전군 명령을 우선한다. 순회 뒤 요청을 비운다.
- unit_orders.issue를 Python 런타임 f_issue로 옮겨 EPScript와 Python 콜백이 같은 명령 구현을 사용한다. 이동 6·어택땅 14이며 Order 트리거는 쓰지 않는다.
- 이 변경은 생성·배열·함수 포인터·순회 기반이다. 7·8·9번 버튼의 공통 시전 명령 입력, 추가 영웅 추첨·생성, 그룹 간 병력 이관, 마나·쿨다운과 액티브 효과는 후속 작업이다.
- 빌드·테스트·별도 코드 검증은 실행하지 않았다.

### 후속 병력 배정 규칙

- 영웅이 늘어나면 새 병력을 활성 영웅들의 부대에 균등 배정한다. 균등의 기준과 영주 사망 시 처리 방식은 구현 시 정한다.
- 생산 건물의 랠리가 특정 아군 영웅 유닛을 가리키면 균등 배정보다 우선해 그 영웅의 부대에만 배정한다. 좌표가 아니라 랠리 대상 유닛 참조를 확인해야 한다.
- 배정은 생성 경로에서 목적 슬롯을 정해 한 번만 등록하는 방식으로 구현한다. 먼저 영주 부대에 넣었다가 다른 그룹에도 중복 추가하지 않는다.
- 현재 변경에서는 위 균등·랠리 배정은 아직 구현하지 않았고 모든 신규 병력을 영주에게 연결한다.

## 슬롯과 등장 제한

- 공통 영주 구이 몬태그는 별도다.
- 추가 영웅은 P1~P7 각각 3슬롯, 동시에 최대 21명이다. 슬롯 번호는 클래스와 무관하며 전사·궁수·법사 어느 영웅이나 배정할 수 있다.
- 초기 명단은 전사·궁수·법사 각 4명, 총 12명이다. 세력 간 같은 영웅의 중복 등장은 허용한다.
- 같은 세력 내 동일 영웅 금지와 동일 클래스 최대 2명은 제안 단계이며 아직 확정하지 않았다. 사망 후 추첨 복귀 규칙도 후속 확정한다.
- 장기적으로 영웅 데이터 100~200종을 준비하고 21개 실체 슬롯을 재사용하는 구조를 목표로 한다.

## 버튼과 마나

- 7번: 소속 UnitGroup 부대 공격(지점 지정, 어택땅 14).
- 8번: 소속 UnitGroup 부대 이동(지점 지정, 이동 6).
- 9번: 영웅 고유 능력. 패시브 설명 / 즉발 / 지점 지정 / 유닛 대상 중 하나다.
- 빌드 때 영웅별 버튼 템플릿을 만들고, 영웅 배정 시 전용 슬롯의 버튼셋 연결을 교체한다. 공유 템플릿 자체를 런타임에 덮어쓰지 않는다.
- 슬롯 배정 때 Spellcaster 속성·현재 마나·버튼을 함께 설정한다. 실제 네이티브 마법 사용 조건과 선택 화면 갱신은 구현 전에 확인해야 한다.
- 소스 검토상 버튼셋과 마나 속성 변경은 가능하지만 인게임 검증은 아직 하지 않았다. 네이티브 최대 마나는 일반 200/영웅 속성 250 등의 별도 규칙을 따른다.
